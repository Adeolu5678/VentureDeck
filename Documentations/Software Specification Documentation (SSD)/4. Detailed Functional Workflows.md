# Part IV: Detailed Functional Workflows

This section documents all major user workflows in VentureDeck, covering both MVP features and advanced Phase 2 functionality.

---

## 4.1. Workflow: Project & Workspace Creation (The Forge)

This workflow describes how an Entrepreneur transforms an idea into a published project and active workspace.

### Actors
- **Primary:** Entrepreneur

### Preconditions
- User is authenticated and has role set to "entrepreneur"

### Steps

1. **Initiation:** User clicks "Create Project" from the dashboard.
2. **Step 1 - Essentials:**
   - User inputs Project Name, Tagline, and Industry.
   - User uploads a high-resolution logo (optional).
   - User selects project Stage (idea, mvp, seed, series-a, series-b, growth).
   - User enters geographic Location (optional).
3. **Step 2 - The Pitch:**
   - User fills in full Description.
   - (Optional) User uploads a PDF Pitch Deck.
4. **Step 3 - The Ask:**
   - User sets Funding Goal (USD).
   - User sets Equity Offered (%).
   - User adds Tags for discoverability.
5. **Review & Publish:**
   - User clicks "Publish" (or saves as Draft).
   - Client calls `mutation projects.create(data)`.
   - **System Actions:**
     - Creates `projects` record with status `published` (or `draft`).
     - Creates `workspaces` record (Name = Project Name).
     - Adds Owner to `workspaces.members` with "Owner" role.
     - Triggers initial traction score calculation.

### Post-conditions
- Project is live on the marketplace (if published).
- Collaborative workspace is ready for team members.
- Project appears in investor search results.

## 4.2. Workflow: Applying & Interviewing

This workflow describes the hiring/teaming process for Talent joining projects.

### Actors
- **Primary:** Talent (Builder)
- **Secondary:** Project Owner (Entrepreneur)

### Preconditions
- Applicant is authenticated
- Project is in "published" status

### Steps

1. **Discovery:** Talent browses project marketplace and finds interesting project.
2. **Application:**
   - Talent clicks "Apply to Join" on project page.
   - Talent selects a role (e.g., "Developer", "Designer", "CTO").
   - Talent can use a saved Application Template or write custom message.
   - Client calls `mutation applications.apply(projectId, role, message)`.
3. **Notification:** 
   - System creates notification for project owner.
   - Application appears in owner's Applications tab.
4. **Review:**
   - Founder reviews application in their dashboard.
   - Founder views applicant's profile, skills, and certifications.
5. **Interview:**
   - Founder clicks "Start Interview".
   - Client calls `mutation conversations.create(applicationId)`.
   - System creates conversation of type `interview`.
   - A private chat opens with the Application as context header.
6. **Verification:** Founder chats with applicant to verify skills.
7. **Decision:**
   - **Accept:** Founder clicks "Accept Applicant".
     - System updates application status to `accepted`.
     - System adds applicant to `workspaces.members`.
     - Applicant receives notification and gains workspace access.
   - **Reject:** Founder clicks "Reject".
     - System updates application status to `rejected`.
     - Applicant receives notification.

### Post-conditions
- Accepted: User is a workspace member with assigned role.
- Rejected: Application is closed, user notified.

## 4.3. Workflow: Workspace Communication

### General Chat
- Accessible to all members of the workspace.
- History is persistent (new members see past messages).
- Members can create custom channels for specific topics.

### Direct Messaging
- Members can click on any other member to start a private DM.
- DMs are conversations of type `direct`.
- Messages support text and optional image attachments.

### Channel Management
- Workspace owner can create public or private channels.
- Private channels require explicit member addition.
- Channels can be archived (isClosed = true).

## 4.4. Workflow: Certification Verification

### Actors
- **Primary:** User (Entrepreneur/Talent)
- **Secondary:** Admin

### Steps

1. **Upload:** User navigates to Profile → Certifications.
2. **Submit:**
   - User enters certification title (e.g., "AWS Solutions Architect").
   - User uploads certificate image as proof.
   - Client calls `mutation certifications.upload(title, imageUrl)`.
   - Status is set to `pending`.
3. **Queue:** Certification appears in Admin's "Verification Queue".
4. **Review:** Admin views the proof image and certification details.
5. **Decision:**
   - **Verify:** Admin clicks "Verify".
     - Status → `verified`, `verifiedAt` timestamp set.
     - Blue checkmark badge appears on user profile.
   - **Reject:** Admin clicks "Reject".
     - Status → `rejected`.
     - User notified of rejection.

### Post-conditions
- Verified: Certification displays with verification badge.
- Rejected: User may resubmit with better proof.

## 4.5. Workflow: Deal Negotiation (Direct Messaging)

This workflow describes direct communication between an Investor and a Founder.

### Actors
- **Primary:** Investor
- **Secondary:** Founder (Entrepreneur)

### Steps

1. **Initiation:** Investor clicks "Contact Founder" on a project page.
2. **Check Existing:** 
   - System checks for existing conversation between these users.
   - If exists, redirects to existing conversation.
3. **Create Channel:**
   - If none exists, client calls `mutation conversations.createDirect(founderId, projectId)`.
   - System creates conversation of type `direct`.
4. **Messaging:**
   - Real-time messaging with Convex subscriptions.
   - Both parties can share documents/images.
   - Project context displayed in conversation header.
5. **Follow-up Actions:**
   - Investor can express interest via Soft Circle.
   - Founder can share Data Room access.
   - Either party can request legal documents.

## 4.6. Workflow: Search and Discovery

### Basic Discovery
- **Trigger:** Investor visits "Deal Flow" or Projects page.
- **Query:** System loads published projects.
- **Display:** Projects shown in grid/list with key metrics.
- **Real-time:** New matching projects appear instantly.

### Filtered Discovery
1. User selects filters (Industry, Stage, Funding Range, Tags).
2. Client calls `query savedSearches.runFilters(filters)`.
3. Results display matching projects sorted by traction score.
4. User can save the search for later use.

### Saved Search Execution
1. User selects a saved search from their list.
2. System runs the saved filters.
3. User can enable alerts for new matches.

## 4.7. Workflow: Milestone Updates (Living Pitch Deck)

### Actors
- **Primary:** Entrepreneur
- **Secondary:** Investors (followers)

### Steps

1. **Create Milestone:**
   - Founder navigates to Project → Milestones tab.
   - Enters title (e.g., "First 100 Users"), description, and target date.
   - Client calls `mutation milestones.create(projectId, data)`.
   - Status is `pending`.
2. **Mark Complete:**
   - When milestone is achieved, Founder clicks "Mark Complete".
   - Status → `completed`.
   - System recalculates project traction score.
3. **Verify (Optional):**
   - Admin or verified user can verify the milestone.
   - Status → `verified`.
   - Higher impact on traction score.
4. **Notify:**
   - System notifies all investors who "Follow" the project.
5. **Display:**
   - Milestone appears on Project Detail page timeline.
   - Timeline shows chronological achievement history.

### Impact on Traction Score
- Pending milestones: 0 points
- Completed milestones: +3 points each (up to 15)
- Verified milestones: +5 points each (up to 20)

## 4.8. Workflow: Micro-Bounties

### Actors
- **Stage 1:** Entrepreneur (creates bounty)
- **Stage 2:** Talent (claims and submits)
- **Stage 3:** Entrepreneur (reviews)

### Steps

1. **Create Bounty:**
   - Founder navigates to Project → Bounties tab.
   - Enters title, description, and reward (e.g., "$500" or "0.1% Equity").
   - Status: `open`.
2. **Claim Bounty:**
   - Talent views available bounties and clicks "Claim".
   - Status → `assigned`, `assigneeId` set.
   - Other users cannot claim.
3. **Work & Submit:**
   - Talent completes the work.
   - Talent submits via form with:
     - `submissionUrl`: Link to PR, file, or deliverable
     - `submissionNote`: Explanation of work done
   - Status → `submitted`.
4. **Review:**
   - Founder reviews submission.
   - **Approve:** Status → `completed`, then `paid` (when payment processed).
   - **Reject:** Status returns to `assigned` or `open`, `reviewNote` added.
5. **Payment:**
   - Founder marks bounty as paid (external payment).
   - Status → `paid`.
   - Talent's profile shows "Bounty Completed" achievement.

## 4.9. Workflow: Soft Circle Commitment

### Actors
- **Primary:** Investor

### Steps

1. **Express Interest:**
   - Investor clicks "Soft Circle" button on project page.
   - Modal opens for commitment details.
2. **Input Amount:**
   - Investor enters amount (e.g., $25,000).
   - Status: `interested`.
3. **Confirm Commitment:**
   - Investor can upgrade to `committed` status.
   - This is a stronger signal of intent.
4. **Display:**
   - Project's "Committed" progress bar updates.
   - Shows "60% Soft Circled" relative to funding goal.
5. **Privacy:**
   - Individual investor names hidden from public.
   - Only project Founder sees who committed.
   - Founder can change status to manage deal flow.

### Impact on Traction Score
- Each active soft circle: +4 points (up to 20)
- Total soft circle amount influences weight

## 4.10. Workflow: Vouching

### Actors
- **Primary:** Voucher (verified user)
- **Secondary:** Vouchee (recipient)

### Steps

1. **Initiate:** User A visits User B's profile.
2. **Vouch Action:** User A clicks "Vouch for [Name]".
3. **Context Input:**
   - User A selects relationship type (e.g., "Former Co-founder", "Worked together", "Investor").
   - User A writes endorsement text.
4. **Submit:** Client calls `mutation vouches.create(targetId, relationship, text)`.
5. **Display:** Vouch appears on User B's profile in "Vouches" section.

### Vouch Display
- Shows voucher's name, avatar, and verification status
- Relationship context displayed
- Endorsement text shown
- Creates network of trust visible to other users

## 4.11. Workflow: AI Deal Scoring

### Trigger
- Automatic: Daily scheduled recalculation
- Manual: Founder requests score refresh
- Event-driven: After milestone completion, new follower, soft circle change

### Calculation Components

| Component | Weight | Factors |
|-----------|--------|---------|
| Milestones | 20% | Count of completed/verified milestones |
| Soft Circles | 20% | Amount committed relative to goal |
| Followers | 15% | Number of investor followers |
| Applications | 15% | Number of team applications |
| Team Completeness | 10% | Workspace member count |
| Pitch Deck | 10% | Whether pitch deck is uploaded |
| Legal Docs | 10% | Whether legal docs exist |

### Process

1. System retrieves all relevant data for project.
2. Each component calculated to a 0-10 or 0-20 score.
3. Components weighted and summed.
4. Final score normalized to 0-100.
5. Score and breakdown stored on project record.
6. Projects sortable by traction score in marketplace.

## 4.12. Workflow: Due Diligence Data Rooms

### Create Data Room

1. **Initiation:** Founder navigates to Project → Data Room tab.
2. **Configuration:**
   - Enters room name and description.
   - Selects access type: `invite_only` or `nda_required`.
   - Optionally sets expiration date.
3. **Creation:** System creates `dataRooms` record.

### Upload Documents

1. Founder clicks "Upload Document" within data room.
2. Selects file from device.
3. File uploaded to Convex Storage.
4. `dataRoomDocuments` record created with metadata.

### Grant Access

1. Founder clicks "Grant Access" and selects user.
2. System creates `dataRoomAccess` record with status `active`.
3. If NDA required, access pending until `ndaSignedAt` is set.
4. Investor receives notification of access grant.

### Investor Viewing

1. Investor navigates to shared data room.
2. System verifies access status and expiration.
3. Document list displayed to authorized investor.
4. Each document view logged (`viewCount`, `lastViewedAt`).

### Revoke Access

1. Founder clicks "Revoke" on user's access.
2. Status → `revoked`.
3. Investor immediately loses access.
4. Audit trail preserved for record.

### Audit Trail

- All access grants/revocations logged.
- Document view counts tracked.
- Last viewed timestamps recorded.
- Founder can view complete access log.

## 4.13. Workflow: Enhanced Matchmaking

### Investor Setup

1. Investor configures preferences in Settings.
2. Enters investment thesis:
   - Preferred industries
   - Preferred stages
   - Investment range (min/max)
   - Geographic preference
   - Minimum traction score threshold
3. Settings saved to user profile.

### Match Calculation

1. Investor views "Recommended for You" section.
2. System calls `query matchmaking.getMatches()`.
3. Algorithm processes each published project:
   - Industry match: Does project industry match preferences?
   - Stage match: Is project stage in preferred list?
   - Investment range: Is funding goal within investor range?
   - Location match: Does geography align?
   - Traction score: Does project meet minimum score?
4. Each factor weighted and scored.
5. Projects ranked by total match score.

### Match Explanation

1. Investor clicks "Why this match?" on a project.
2. System calls `query matchmaking.getMatchExplanation(projectId)`.
3. Detailed breakdown displayed:
   - Each matching category
   - Match status (matched/not matched)
   - Reason text
   - Score contribution

## 4.14. Workflow: Saved Searches & Alerts

### Create Saved Search

1. Investor applies filters in project discovery.
2. Clicks "Save Search".
3. Enters search name.
4. Optionally enables alert notifications.
5. System saves filter configuration to `savedSearches`.

### Run Saved Search

1. Investor selects saved search from list.
2. System runs filters against current projects.
3. Results displayed with projects matching criteria.
4. `lastRunAt` timestamp updated.

### Alerts (Future Enhancement)

1. Scheduled job checks for new projects matching saved searches.
2. If new matches found, notification created.
3. Investor notified of new opportunities.

## 4.15. Workflow: Application Templates

### Create Template

1. User navigates to Settings → Application Templates.
2. Clicks "Create Template".
3. Enters:
   - Template name (e.g., "CTO Application")
   - Target role
   - Message body
4. Optionally marks as default.
5. Limit: 5 templates per user.

### Use Template

1. When applying to a project, user selects "Use Template".
2. Template list shown sorted by usage.
3. Selected template populates role and message fields.
4. User can customize before submitting.
5. `usageCount` incremented on use.

## 4.16. Workflow: Legal Document Generation

### Available Templates

| Template | Use Case |
|----------|----------|
| SAFE | Simple Agreement for Future Equity |
| NDA | Non-Disclosure Agreement |
| Advisor Agreement | Advisory engagement terms |
| Founder Agreement | Co-founder equity split |
| Convertible Note | Debt convertible to equity |
| Term Sheet | Non-binding investment terms |
| Investment Agreement | Binding investment contract |

### Generation Process

1. Founder navigates to Project → Legal Documents.
2. Selects template type.
3. System loads template with placeholders.
4. User fills in variables:
   - Company name, investor name
   - Amounts, percentages, dates
   - Custom terms
5. System generates formatted document.
6. Document stored in `legalDocs` with `draft` status.

### Signing Workflow

1. Parties review generated document.
2. (External) Parties sign document.
3. Founder marks document as signed.
4. Status → `signed`, `signedAt` and `signerId` set.

## 4.17. Workflow: Project Analytics

### View Tracking

1. When any user views a project page:
   - System calls `mutation analytics.trackView(projectId, fingerprint)`.
   - Creates `projectViews` record.
   - Fingerprint used for unique view counting.

### Daily Snapshots

1. Scheduled job runs at midnight UTC.
2. For each published project:
   - System aggregates previous day's views.
   - Captures current follower count.
   - Captures soft circle totals.
   - Captures application count.
   - Captures current traction score.
3. Creates `projectAnalytics` record.

### Dashboard Display

1. Founder views Project → Analytics tab.
2. System calls `query analytics.getProjectAnalytics(projectId, days)`.
3. Dashboard displays:
   - Today's real-time metrics
   - Historical trends (charts)
   - Traction score breakdown
   - Comparison to platform averages

3. Feed aggregates:
   - Applications to user's projects
   - Soft circles on user's projects
   - New followers on user's projects
   - Milestone completions
   - Bounty status changes
   - Friend requests

### Discover Activity Feed

1. Investor views Discover/Network section.
2. System calls `query activity.getDiscoverActivity()`.
3. Feed shows platform-wide activity:
   - New projects published
   - Projects reaching funding milestones
   - High traction score achievements
4. Helps investors discover trending opportunities.

## 4.19. Workflow: Friend System

### Send Friend Request

1. User A visits User B's profile.
2. Clicks "Add Friend".
3. Optionally adds request message.
4. System creates `friends` record with status `pending`.
5. User B receives notification.

### Accept/Reject Request

1. User B views pending requests.
2. **Accept:** Status → `accepted`.
   - Friendship bidirectional.
   - Users appear in each other's friends list.
3. **Reject:** Status → `rejected`.
   - Request dismissed.

### Friends List

- Shows all accepted friends.
- Allows quick DM access.
- Can remove friends (deletes relationship).

## 4.20. Workflow: Admin Dashboard

### Certification Queue

1. Admin views pending certifications.
2. For each certification:
   - Views proof image.
   - Verifies or rejects.
3. Users notified of decisions.

### User Moderation

1. Admin can search/filter users.
2. Actions available:
   - Toggle admin status.
   - Suspend user (affects verification status).
3. Changes logged (audit trail placeholder).

### Project Moderation

1. Admin can search/filter projects.
2. Actions available:
   - Change project status.
   - Close inappropriate projects.
3. Project owners notified of moderation actions.

### Feature Flag Management

1. Admin views all feature flags.
2. Can enable/disable flags.
3. Changes take effect immediately platform-wide.
4. Used for:
   - Rolling out new features gradually.
   - Disabling problematic features.
   - A/B testing infrastructure.

   - Update Display Name, Bio, Avatar.
   - Manage Skills and Interests tags.
   - Configure LinkedIn/GitHub URLs.
3. **Investor Thesis (Investors only):**
   - Set preferred industries and stages.
   - Configure investment range.
   - Set minimum traction score.

### Account Settings

1. **Notifications Tab:**
   - Toggle email notifications.
   - Toggle push notifications.
   - Configure digest frequency (daily/weekly/never).
2. **Privacy Tab:**
   - Set profile visibility (public/private).

### Application Templates

1. View/create/edit/delete application templates.
2. Set default template for quick applications.

### Certifications
